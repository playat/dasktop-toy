## 动作之间加停顿（`animGap`）

用户反馈「两个视频之间间隔太短，不用那么快做下一个动作，希望更真实；可以用随机时间或根据设备参数（CPU 频率等）决定」。

**做法**：`window.py` 新增 single-shot `_gap_timer`，`_after_oneshot` 不再直接 `_roll_next`，走
`_schedule_next(kind)`。间隔 = `random(minMs,maxMs)` + 动作惩罚 `actionExtraMs×U(0.35,1)`
+ `longPauseChance` 概率加 `longPauseMs×U(0.5,1)`，再 `×(1+loadInfluence×负载)`。
改动的入口：`_drive_move`→`"move"`、`_drive_throw` 落定→`"throw"`、无点击素材→`"click"`；
`_play()` 里 `_gap_timer.stop()` 让新动画作废待定掷骰；`set_external_lock(False)` 补排一次防僵住。
静止期间**定格在素材末帧**——提示词强制「首尾回到标准站姿」，所以等于站着不动，且不额外解码。

**负载调制**：`_LoadMeter` 用 `GetSystemTimes` 差分算 CPU 占用（posix 退 `getloadavg`）。
第一版直接用绝对占用率，被桌宠自己解码的负载顶满，2~5s 的配置实测跑出 29s 静止。改成**减基线**：
首次采样当 baseline，只报超出部分（`base` 只在更闲时下调）。修正后实测静止 3.8s / 6.1s，与排期一致。

**默认值两次下调**：初版 2500~7000 + longPause 20000 跑出 29~42s 静止，太夸张；
最终 `2000~5500 / extra 2000 / long 12%@12000 / load 0.6`，嫌快改 `minMs/maxMs`，恢复原版连播写 `"enabled": false`。

文档：`config.jsonc` 新增 `animGap` 段（含公式注释）+ 顶部字段清单，README §1 功能点与 §6 调参段同步。

## 动作间隔改成「播待机」而不是「定格末帧」

用户反馈：动作播完后到下一个视频之间的几秒一直停在末帧，看着像卡住。改成动作播完立刻切待机动画（loop），
间隔到了再切下一个动作。`window.py` 新增 `_idle_then(kind)` = `_hold_idle()` + `_schedule_next(kind)`
（**顺序不能反**，`_play()` 会 `_gap_timer.stop()`，反了计时器刚起就被掐死）。`_after_oneshot`、
`_drive_move` 结束、`_drive_throw` 落定、`mouseRelease` 无点击素材四处改走 `_idle_then`；
`_roll_next` 的 drag/throw 分支、`_on_gap_elapsed`、`set_external_lock(False)` 保持裸 `_schedule_next`
（被拖/被甩/被占用时画面本身有意义，不该切待机）。

坑：同一段待机正在播时 `AnimationPlayer.play()` 会返回 False（同名未 finished 就拒播），
`_play()` 因此不改 `state`，导致画面是待机但 `state` 还停在 `"action"` —— `_hold_idle` 里补了 else 分支归位。
实测：动作后 0.000s 切待机、gap 5.2s 到期正常切下一个动作、走位结束同样切待机；
`enabled=false` 仍是无缝连播。文档同步 README §1/§6、`config.jsonc` 的 animGap 注释、window.py 模块 docstring。

## 绿幕抠像：灰边 + 去水印残留

用户反馈「灰点很多，尤其视频生成水印」「右下角和左上角有去水印后的残留灰白点」。
**去查了上游**（github raw `scripts/chroma_step02.py`）：判据就是「色相 70~170 + sat≥0.15 + val≥0.15」，
和本项目一模一样；上游 commit 自己只宣称「绿幕清除 99.6%」，后来**91 个动作全量改用 PR 手工抠像**
（pr_import_step02.py）。所以这不是我抄错，是这套判据的天花板。

诊断（`video/src` 两个素材，1280×720）：
- 角色左边缘扫描线：绿幕 (113,140,112) sat 0.20 → 4px 过渡带里 sat 掉到 0.08~0.12、颜色变灰
  (101,104,94)，sat<0.15 被**判为前景** → 一圈灰边。这就是「灰点」主体。
- 左上角有一串「豆包AI生成」白字，`watermark_mask_v5.mkv` 只盖了底部横条（y 611~719），
  左上角**完全没盖** → 白字 sat<0.15 保留 → 一片灰白块。用户说的左右两角正好对上。
- mask 覆盖的底部，4 向插值填成淡绿 (176,196,176) sat 0.10，同样被判前景 → 右下角也留残影。

改动（`make_pet_webm.py`，均在 `key_frame`）：
1. `SAT_MIN` 0.15→0.07，并加 `G - max(R,B) >= 2`。单降 sat 会把白裙啃掉，加「绿通道占优」后
   角色核心保留 99.4%+，削掉的全是边缘灰带/水印区/散点。
2. 新增 `_strip_watermark()`：亮(val>0.70) + 无彩(sat<0.13) + 角色外接框外 + 单块扁长
   (宽≥2.5×高、高≤12%画面) + 面积<2% → 直接 alpha=0。用 `_split_regions` 切块逐个判。
   宁漏不错：特效/光斑有形状和面积兜着，误伤风险低。

验证：成品全帧扫描，左上角白字 241 帧最多 0 px（改前源帧有 2179px）；右下角灰白点 7→0；
整帧不透明率 14.57%→13.76%；离屏端到端重跑 71s 正常出片。
**已生成的 webm 不会自动更新**，要 `make_pet_webm.py --force` 重跑；只跑了临时目录，没覆盖 assets/webm。
